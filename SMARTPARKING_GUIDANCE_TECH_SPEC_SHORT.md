# Техническое задание
## PGS (Parking Guidance Service) на FastAPI для проекта SmartParking

Версия: 2.0  
Дата: 2026-05-20  
Статус: рабочая сокращенная версия

## 1. Цель

Разработать отдельный микросервис `PGS (Parking Guidance Service)` на `FastAPI`, который будет:

- принимать события от guidance-камер;
- определять занятость парковочных мест;
- считать свободные места по зонам, рядам и уровням;
- управлять LED-табло с указанием свободных мест;
- отдавать агрегированные данные в `SmartParking` и dashboard.

Важно: в данной версии сервис **не назначает конкретное место конкретной машине**.  
Сервис работает по модели `free-space guidance`:

- показывает направление;
- показывает зону/ряд;
- показывает количество свободных мест.

## 2. Общая идея решения

Новая реализация делится на две отдельные системы:

- `SmartParking`
  - въезд/выезд;
  - `ParkingSession`;
  - биллинг;
  - шлагбаум;
  - основной backoffice.
- `PGS`
  - зоны;
  - ряды;
  - места;
  - статусы `FREE / OCCUPIED`;
  - счетчики свободных мест;
  - LED-табло;
  - события от guidance-камер.

Главный принцип:

- `SmartParking` не владеет парковочными местами;
- `PGS` не владеет парковочными сессиями и оплатой.

## 3. Исходные данные проекта

- общее количество парковочных мест: `1800`;
- ориентировочное количество guidance-камер: `150-300`;
- используются специализированные guidance-камеры со встроенным определением статуса места;
- используются отдельные LPR-камеры на въезде и выезде;
- используются LED-экраны маршрутизации;
- при необходимости используются LED-индикаторы над местами.

## 4. Границы первой версии

### Входит в объем

- хранение структуры парковки: зона -> ряд -> место;
- прием событий от guidance-камер;
- хранение текущего статуса каждого места;
- пересчет свободных мест по зонам и рядам;
- управление LED-экранами;
- API для получения summary;
- интеграция со `SmartParking` по REST API;
- симуляция событий для разработки без реальных камер.

### Не входит в первую версию

- назначение конкретного места конкретной машине;
- резервирование места;
- TTL резерва;
- персональный маршрут для автомобиля;
- привязка места к конкретному номеру машины;
- логика оплаты внутри guidance-сервиса.

## 5. Бизнес-логика

Сервис работает по простой схеме:

1. Guidance-камера передает событие о месте.
2. `PGS` обновляет статус места.
3. Сервис пересчитывает количество свободных мест по зоне/ряду.
4. Сервис отправляет обновленные значения на LED-табло.
5. `SmartParking` и dashboard при необходимости запрашивают summary у PGS.

Пример поведения:

- было `Zone A -> 25`
- одно место в зоне `A` занялось
- стало `Zone A -> 24`

## 6. Почему выбран отдельный FastAPI сервис

`PGS` выносится в отдельный микросервис, потому что:

- он работает как device/event-oriented контур;
- он принимает поток событий от оборудования;
- его логика слабо связана с оплатой и `ParkingSession`;
- его можно масштабировать и разворачивать отдельно;
- он может жить независимо от ядра `SmartParking`.

`FastAPI` выбран, потому что:

- хорошо подходит для API и event-ingest сценариев;
- удобен для async I/O и интеграции с устройствами;
- легче для отдельного легкого сервиса, чем полноценный Django-монолит;
- не требует переносить в новый сервис тяжелый backoffice SmartParking.

## 7. Рекомендуемая архитектура

### Основные компоненты

- `pgs-api` на `FastAPI`
- `pgs-db` на `PostgreSQL`
- `pgs-worker` для фоновых задач
- `redis` для очередей, realtime или кэша
- `SmartParking` как отдельный соседний сервис

### Рекомендуемый стек

- `FastAPI`
- `Pydantic`
- `SQLAlchemy 2.0`
- `Alembic`
- `PostgreSQL`
- `Redis` при необходимости
- отдельный worker-контур для фоновых задач

### Контуры ответственности

`SmartParking`:

- LPR-въезд/выезд;
- `ParkingSession`;
- биллинг;
- barrier control;
- основной admin/backoffice.

`PGS`:

- `ParkingZone`
- `ParkingRow`
- `ParkingSpot`
- `GuidanceDisplay`
- `SpotOccupancyEvent`
- счетчики свободных мест;
- команды на LED-экраны.

## 8. Необходимое оборудование

### Источник событий занятости

`PGS` не работает напрямую с SDK/IP-камерами. Он принимает уже нормализованные события занятости от внешнего источника, например `unv-service`.

Внешний источник событий должен:

- определять статус места `FREE / OCCUPIED`;
- отправлять идентификатор места и новый статус в `PGS`;
- при необходимости передавать исходный payload производителя;
- обеспечивать стабильную доставку событий в условиях конкретного паркинга.

### LPR-камеры

LPR-камеры остаются в контуре `SmartParking` и используются только для:

- распознавания номера на въезде/выезде;
- создания и закрытия `ParkingSession`.

### LED-экраны

Маршрутные LED-экраны должны уметь показывать:

- стрелку направления;
- код зоны или ряда;
- количество свободных мест.

Пример табло:

- `A -> 24`
- `B <- 8`
- `P2 -> 41`

### LED-индикаторы над местами

Это необязательный компонент первой версии. При наличии они могут показывать:

- `FREE` -> зеленый;
- `OCCUPIED` -> красный;
- `OFFLINE/ERROR` -> сервисный режим.

## 9. Основные сущности данных

Минимально нужны:

- `ParkingZone`
- `ParkingRow`
- `ParkingSpot`
- `SpotOccupancyEvent`
- `GuidanceDisplay`
- `DisplayCommand`

Важно:

- все эти сущности хранятся в отдельной БД PGS;
- `SmartParking` не должен напрямую писать в эти таблицы.

## 10. Основные API

### API приема событий о местах

- `POST /api/v1/spot-events`

Событие о месте должно содержать:

- идентификатор места;
- новый статус места;
- timestamp;
- source внешнего сервиса;
- event id, если он есть;
- исходный payload производителя.

### API для интеграции со SmartParking и dashboard

- `GET /api/v1/zones/summary`
- `GET /api/v1/rows/summary`
- `GET /api/v1/spots`
- `GET /api/v1/displays/summary`
- `GET /api/v1/health`

### API для симуляции

- `POST /api/v1/spot-events`

Этот endpoint можно использовать и для симуляции, и для интеграции с внешним сервисом событий.

## 11. Нефункциональные требования

Сервис должен:

- обрабатывать поток событий занятости от внешнего сервиса в near real-time;
- быть устойчивым к дублирующимся событиям;
- обновлять состояние места до `2 секунд`;
- обновлять LED-табло до `3 секунд`;
- отдавать актуальный summary до `5 секунд`;
- сохранять журнал событий и ошибок оборудования;
- быть готовым к горизонтальному масштабированию API-слоя.

## 12. Этапы реализации

### Этап 1

- каркас FastAPI-сервиса;
- БД и миграции;
- модели зон, рядов, мест и событий занятости.

### Этап 2

- ingest событий от guidance-камер;
- хранение и обновление occupancy.

### Этап 3

- summary API по зонам и рядам;
- логика пересчета свободных мест.

### Этап 4

- интеграция LED-экранов;
- обновление счетчиков и направлений.

### Этап 5

- интеграция со SmartParking по REST;
- симуляция и эксплуатационная стабилизация.

## 13. Критерии приемки

Сервис считается принятым, если:

1. В системе заведены зоны, ряды, места и камеры.
2. Для каждого места хранится актуальный статус.
3. Guidance-камера меняет статус нужного места.
4. Сервис корректно считает свободные места по зонам.
5. LED-экраны получают и показывают актуальные значения.
6. `SmartParking` может получить summary через API.
7. Сервис можно полноценно тестировать без реальных камер через симуляцию.

## 14. Схемы

### 14.1 Общая схема системы

```text
 +--------------------+        +----------------------+
 |   Guidance Cameras | -----> |         PGS          |
 | FREE / OCCUPIED    |        | FastAPI + PostgreSQL |
 +--------------------+        +----------+-----------+
                                           |
                          +----------------+----------------+
                          |                                 |
                          v                                 v
                 +-------------------+             +------------------+
                 |   LED Displays    |             |  SmartParking    |
                 | Arrow + Free Qty  |             | Session/Billing  |
                 +-------------------+             +------------------+
```

### 14.2 Поток обработки события

```text
Guidance Camera
      |
      v
POST /api/v1/camera-events
      |
      v
Normalize event
      |
      v
Update ParkingSpot.status
      |
      v
Recalculate free places by zone/row
      |
      v
Send values to LED display
      |
      v
Expose summary via API
```

### 14.3 Связь со SmartParking

```text
SmartParking
   |
   | GET /api/v1/zones/summary
   v
PGS
   |
   | returns:
   | Zone A = 24 free
   | Zone B = 8 free
   v
SmartParking dashboard / UI
```

### 14.4 Deployment схема

```text
nginx / gateway
 ├─ smartparking-web
 ├─ smartparking-db
 ├─ pgs-api
 ├─ pgs-db
 ├─ redis
 └─ pgs-worker
```

## 15. Итог

Первая версия `PGS` должна быть отдельным `FastAPI` микросервисом, который решает одну основную задачу:

- показывает, **где есть свободные места**, а не **какое место назначено конкретной машине**.

Такой подход дает:

- чистую границу между `SmartParking` и `PGS`;
- более простой первый релиз;
- отдельное масштабирование PGS-контура;
- удобную интеграцию с оборудованием;
- возможность разрабатывать и тестировать сервис без реальных камер.
